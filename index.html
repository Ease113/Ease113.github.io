프로젝트 개요

경험에 의존하던 다품종 제조 라인의 생산순서 결정을 데이터 기반으로 시뮬레이션하고 비교하는 스마트팩토리 플랫폼의 MVP입니다. XGBoost로 전환 비용을 예측하고 OR-Tools로 순서를 최적화하는 파이프라인을 구축했습니다.

파이프라인 구조
설계 판단 1비결정적 연산 분리를 위한 API 계약 설계 (/optimize 단일 호출)
문제
운영자가 화면에서 순서를 조정할 때마다 최적화 알고리즘(OR-Tools)이 재호출되면 비교 기준선이 계속 흔들려 추천안과의 비용 비교가 불가능해짐.
해결
페이지 진입 시 /optimize를 1회만 호출하여 추천 순서를 고정하고, 이후의 사용자 조정에 따른 변경 사항은 가벼운 /predict 연산으로 재계산하도록 API 설계.
성과
무거운 비결정적 연산 비용을 절감하고, 사용자에게 명확하고 고정된 의사결정 비교 기준선 제공.
설계 판단 2시스템 복원성을 위한 계층형 대체 작동(Fallback) 설계
문제
해커톤 및 데모 환경에서 API 키 누락, ML 모델 미학습, 최적화 라이브러리 에러 발생 시 전체 파이프라인이 멈출 위험 상존.
해결
AI 구성요소 실패 시 XGBoost → 결정론적 휴리스틱, OR-Tools → 휴리스틱 탐색, LLM → 템플릿 기반 텍스트로 단계별 다운그레이드되도록 Fallback 로직 구현.
성과
핵심 의사결정 파이프라인의 결함 허용(Fault Tolerance)을 확보하여 안정적인 데모 보장.
설계 판단 3데이터 모델 수준의 모호성 제거 (plan_item_id 분리)
문제
하나의 생산 계획 내에 동일한 제품(SKU)이 중복 배치될 수 있어 sku_id만으로는 정확한 순서 식별이 불가능함.
해결
데이터 모델 설계 시 생산 순서의 기준 식별 키를 sku_id가 아닌 고유한 plan_item_id로 정의.
성과
데이터 모델 수준에서 중복 SKU 배치 문제를 근본적으로 해소하고 순서 식별 모호성 제거.

결과

  • 163개 참가팀 중 온라인 예선 통과 → 오프라인 본선 진출 (2026.05.22)
  • AI 추천안·운영자 조정안 비용 비교 기능 구현
  • AI 구성요소 부분 장애 시에도 전체 파이프라인 정상 동작
05 AI-assisted Engineering

팀 내 유일한 개발 역량 보유 PMO로서, 산출물 프로세스의 자동화를 통한 업무 효율화를 선제적으로 추진했습니다. 이 과정에서 AI 기반 개발 자동화의 한계를 직접 경험하고, 오버 엔지니어링과 범위 이탈(Scope Creep)을 통제하는 설계-검증 워크플로우를 정립하게 되었습니다.

A자동화 시도와 한계 발견 — 3단계 진화

1단계 — GeminiFactory (Gemini + MCP + CLI)
PMO 산출물(요구사항 정의서, 시스템 설계서 등) 자동화를 위해 Gemini를 기반으로 MCP·Skill을 구성하고, 템플릿·아웃풋·컨텍스트 구조를 정의한 CLI 환경을 직접 구축했습니다. Gemini의 성능 한계를 확인한 후 동일한 구조를 Claude로 이식해 산출물 자동화 일부 구현에 성공했고, 이를 플랫폼으로 발전시키는 방향을 시도했습니다.

2단계 — PMO-Assistant (Codex 기반 오케스트레이터)
기존 design → dev → review → PR 하네스 위에 오케스트레이터를 구현해, CMD 백그라운드에서 24/7 자율 실행되는 개발 자동화 플랫폼을 구축했습니다. Reviewer 단계에서 Claude와 Codex의 교차 검증을 적용했고, 최종 검토만 사람이 수행하는 구조로 설계했습니다.

Agent Orchestration 구조 — Codex 기반 / PMO-Assistant

한계와 중단
플랫폼을 운영하면서 구현이 진행될수록 시스템이 초기 설계 범위를 스스로 확장해 가는 문제를 발견했습니다.
매 단계의 확장이 국소적으로는 합리적으로 보여 멈추기 어렵고, 누적되면 최종 결과물이 처음 의도한 설계에서 벗어났습니다.
핵심 문제가 "AI가 코드를 생성할 수 있는가"가 아니라 "구현이 초기 의도 안에 머무를 수 있는가"임을 확인하고 자율 구현을 중단했습니다.
현재 하네스 구조를 단순화하는 방향으로 새로운 설계를 진행 중입니다.

B재정립된 개발 규칙 및 템플릿

복잡한 오케스트레이터 대신, 명시적인 규칙과 설계 문서를 통해 구현 범위를 제어하는 방향으로 전환했습니다.
코드 컨벤션처럼 결정론적으로 검증 가능한 항목은 린터에 위임하고, 자연어 규칙은 도구가 잡을 수 없는 영역(가정 명시·범위 통제·설계 판단)에만 집중했습니다.
