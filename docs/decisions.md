# 이력서 의사결정 기록

> 이력서 구조·표현·전략에 관한 선택과 그 근거. 다음번 수정 시 같은 고민을 반복하지 않기 위함.

---

## D1. 지원 타깃 — "특정 회사 아닌 개발 직무 전반"

**결정**: 특정 회사/도메인을 좁히지 않고, 어느 개발 회사든 통할 만한 일반형으로 작성.

**근거**:
- 빠른 이직이 1순위 목표. 타깃을 좁히면 지원 폭이 줄어듦.
- 토이 프로젝트로 최신 기술 감각을 추가 시그널링할 계획이라, 본 이력서는 "안정적 백엔드 베이스"에 집중.

**적용**:
- 소개 문구를 "Java/Spring 기반 약 2년" 같은 직관적 키워드로 시작.
- 고급 키워드(비결정적 알고리즘 분리, AI 하네스 워크플로우 등)는 SmartFactory 프로젝트 안에 가둠 — 소개에서는 제거.

---

## D2. 섹션 순서 — "시간 순(개발 위 / PMO 아래) 유지"

**결정**: 일반 원칙인 "시간 역순"을 따르지 **않고**, 개발 경력(Lazorte, 2023~2025)을 위에 두고 PMO(2025~현재)를 아래에 둠.

**검토한 대안**:
- (A) 시간 역순 (PMO 위 / 개발 아래) — 일반 채용 원칙. 다른 Claude 세션이 추천.
- (B) 시간 순 (개발 위 / PMO 아래) — **채택**

**근거**:
- 본 직무(지원하는 직무)는 백엔드 개발. 현재 직무는 PMO. **현재 직무 ≠ 지원 직무**인 비대칭 상황.
- 채용 담당자는 첫 항목을 "이 사람의 현재 정체성"으로 읽음. 첫 항목이 "PMO"면 0.5초 만에 "개발 안 한 지 1년 됐네" 박힘.
- 일반 원칙(역순)은 현재 직무가 지원 직무와 일치할 때의 규칙. 정세영 케이스에는 부적합.

**리스크**:
- "최신 경력을 숨겼다"는 인상 가능성 → **D3**의 소개 문구 보강으로 상쇄.

---

## D3. 소개 문구에 "현재 PMO 재직 + 복귀 준비 중" 명시

**결정**: 소개 마지막 단락에 "현재 PMO 재직 중, 백엔드 개발자로 복귀 준비 중"을 한 줄 명시.

**근거**:
- D2(시간 순 유지)의 리스크 상쇄. 시간 순서를 깬 게 아니라 의도적 선택임을 첫 화면에서 드러냄.
- PMO 경력을 숨기려는 것이 아님을 명확히 — 채용 담당자가 "왜 시간 역순이 아니지?" 의심하기 전에 답을 줌.
- "토이 프로젝트로 최신 기술 다루는 중"도 함께 명시해 "공백" 인상 차단.

---

## D4. PMO 섹션 타이틀 — "PMO 경력" 유지 (vs "경력"으로 통합)

**결정**: PMO 섹션을 별도로 두되, 키커에 "백엔드 출신 PMO"를 병기.

**검토한 대안**:
- (A) 개발/PMO 통합해서 "경력" 단일 섹션 — 백엔드 색 강해짐. 단, 면접에서 "제타에서 코드 짰냐"에 매번 부연 필요.
- (B) 분리하되 키커로 정체성 보강 — **채택**

**근거**:
- 정직성. PMO는 PMO. 통합하면 면접 첫 질문이 매번 같은 부연으로 시작됨.
- "백엔드 출신 PMO" 키커는 깎이지 않으면서 약점을 자백하지도 않음.

---

## D5. PMO 직책 표기 — "아키텍처 설계 · PMO" → "PMO"

**결정**: 거추장한 직책 표현 제거. 그냥 PMO.

**근거**:
- 본인 확인: "아키텍처 설계라는 거추장한 직책이 아니다."
- 실제 업무는 일정 관리, 산출물 작성·검토, QA 중심. 아키텍처 설계는 일부 업무지 직책이 아님.
- 이전에 추가했던 "설계 판단 1·2" 블록(ETL 분기 설계, 다단계 행정망 연계)은 오버클레임이라 삭제. 망 연계 경로 정의 사실은 Project 04 bullet으로 흡수.

**보존한 PMO 역할 강조 포인트**:
- "백엔드 출신 PMO" 키커
- 인트로의 "백엔드 개발 경험 기반으로 개발팀과 직접 소통하며 산출물 품질 검토" 문장
- Apache JMeter 성능 테스트 항목 — 개발자스러운 작업으로 명시

---

## D6. AI-assisted Engineering 섹션 — 독립 섹션 폐지, SmartFactory에 압축 편입

**결정**: 기존 "05. AI-assisted Engineering 워크플로우" 독립 섹션 제거. SmartFactory 프로젝트 안에 "개발 환경" 한 단락으로 압축.

**근거**:
- 독립 섹션이면 "개발자가 맞나, 방법론 컨설턴트인가" 인상 위험.
- 같은 내용도 프로젝트 안의 "이렇게 개발했다" 맥락이면 강점이 됨.
- 5개 섹션은 다소 많음. 4개로 정리.

**보존한 내용** (압축 편입):
- AI-assisted Workflow를 직접 정립해 적용했다는 사실
- `CLAUDE.md` 자연어 규칙 운영
- `design-doc.md` 템플릿 게이트웨이 운영

**버린 내용** (이력서에서 제외, `docs/career-facts.md`에 보관):
- 3단계 진화 서사 (GeminiFactory → PMO-Assistant → 한계 발견)
- Agent Orchestration ASCII 다이어그램
- 한계와 중단 과정의 상세 설명

## D7. 프로젝트 섹션 — "해커톤 프로젝트" → "프로젝트"

**결정**: 섹션명을 일반화. 앞으로 토이 프로젝트가 추가될 슬롯으로 활용.

**근거**:
- 현재는 SmartFactory 하나뿐이지만, 토이 프로젝트가 추가될 때마다 자연스럽게 채워질 공간.
- 토이가 채워질수록 "이 사람 계속 코드 짜고 있구나" 신호가 강해져서 PMO 라벨의 약점 상쇄.
- "예정"이나 빈 슬롯 명시는 마이너스라서 하지 않음 — 채워질 때 채움.
